# 以证据为依据的路线图

[English](../ROADMAP.md) | **简体中文**

本路线图列出的是推进条件，而非交付承诺。

## v0.1：让生命周期可检查

已交付：严格的包 Schema、语义检查、五种视图、经过审查的有界修订、撤销、独立的演示数据绑定、本地能力控制、经确认的本地笔记、包的导出/导入/派生、离线解析器、可选的本地模型桥接服务，以及可复现的检查。

推进条件：另一位开发者可以独立运行演示、理解其局限，并在无需帮助的情况下复现迁移闭环。

## v0.2：将同一套生命周期带到手机

已交付：中英双语 UDI Pocket，包含触摸卡片、五个导航标签、安装清单、离线应用资源缓存和手机验收检查。它与 Studio 使用同一份 Core 0.1 定义和运行时，详见[手机使用指南](MOBILE.md)。原生应用商店安装包、跨设备同步和真实手机连接器仍属于后续工作。

## 下一步：验证最难的两个假设

1. 使用未见过的用户请求开展有记录的模型评估。区分有效 JSON 和正确的意图理解。公开不受支持的用例与失败。
2. 请用户复用他人创作的包。测量绑定纠正、理解程度，以及获得有用工作区所需的时间。

推进条件：有证据表明，相比等价的固定配置或整体界面重新生成，修订与迁移能帮助用户。

## 随后：一个真实连接器与一个渲染器适配器

将策略和凭据移入可信网关。增加一个限定资源范围、结果经过验证的只读数据源。为一个已有的声明式渲染器实现注明版本的适配器。在引入外部写操作前，增加并发编辑的事务语义，以及有有效期、仅能使用一次的批准机制。

推进条件：对数据边界进行独立审查，并成功完成一次跨实现的包使用实验。当前两个数据集之间的重新绑定，不足以证明生态系统层面的可移植性。

## 更长远：更广的工作流与注册表

考虑事件与工作流契约、迁移、包完整性、来源、内容治理、能力差异审查和分发。语义图谱与后台智能体是可能的扩展，并非核心思想的前提。

推进条件：反复出现的真实用户需求超出了简单包模型的表达能力。在拥有有用的包和可信的安全模型之前，不应先构建市场。
