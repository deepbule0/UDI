# 用户定义界面：在具备能力的平台中构建个人使用体验的框架

[English](../POSITION-PAPER.md) | **简体中文**

**立场论文草稿 · 应用 v0.4.0 · Core 0.1 研究配置 · 2026 年 10 月 17 日**

## 摘要

应用通常同时提供功能，以及所有人使用这些功能的界面。我们提出**用户定义界面（User-Defined Interface，UDI）**设计框架：平台提供内容、受支持的操作和可用的默认应用，而用户通过智能体或常规控件，塑造自己持久使用的体验。它可以涵盖呈现方式、交互、数据组织与受支持的工作流。用户应当能够试用他人分享的体验，结合自己的数据和权限使用、修改它，再通过熟悉的链接方式分享，无需编程或处理界面文件。可复用定义与私人实例的分离，构成其技术基础。智能体提出有界修订，宿主校验定义并管控数据访问及实际操作。本仓库提供实验性参考实现和研究领域的可执行配置；它并不构成已批准的标准、通用兼容性的证明或新计算范式的证据。

## 1. 问题与价值

平台提供内容、受支持的操作和默认应用。UDI 提出，用户可以在这些能力之上塑造持久的使用体验，而无需创作软件。平台契约定义可用范围，用户选择受支持的信息与操作如何呈现、组织和使用。

领域示例包括阅读队列、学习安排、行程规划、照片组织、效率工作流，以及音乐库或播放布局。这些是说明性应用，并非已实现的集成。UDI 可以用于单个平台内部；组合多个提供方还需要额外的契约、授权和实现工作。

核心问题是：普通用户能否**塑造、保留并分享自己使用应用的方式**，而不必成为开发者，也不会让共享设计获得他人的私人账户权限。终端用户编程、自适应界面、可配置应用和生成式界面已经解决了部分问题。本项目提出的贡献，是将提供方能力、用户创作、受控执行和复用连接为明确、可检验的生命周期。

## 2. 定义与范围

**用户定义界面**是一种持久化、由用户控制的应用使用体验。用户可以通过表达意图或直接控件修改其呈现和受支持的行为，并在不携带个人私有运行状态的前提下复用它。

平台或内容提供方仍负责提供有意义的内容、受支持的功能和可用的默认体验。用户在受支持的范围内，塑造这些内容与功能的呈现、组织和调用方式。提示词可以改变布局、组织收藏，或描述一段受支持的操作流程；它不会凭空创造不存在的服务，也不能覆盖平台策略。

普通用户面对的交互应高于 API 请求、源代码编辑器或文件上传这一层。实现者和高级用户可以使用这些机制，但它们不应成为创作或分享的必经路径。[通用框架](FRAMEWORK.md)将这一产品模型与当前研究领域的 [Core 0.1 配置](SPECIFICATION.md)区分开来。

这一表述和缩写具有历史来源：Wixon、Whiteside、Good 和 Jones 在 CHI 1983 中使用 **user-defined interface（UDI）**，描述围绕用户自发命令迭代形成的电子邮件界面。本项目沿用这一术语，指代这里描述的、由智能体参与的特定框架，不主张首创该名称。参见 [Building a User-Defined Interface，1983](https://michaelgood.info/publications/usability/building-a-user-defined-interface/)。

**界面追随意图（interface follows intent）**是一项目标。对话不总是最好的控件：可预测的设置、直接操作、稳定布局和无障碍仍然重要。智能体对话与常规控件应当提供通向同一组受支持变更的互补路径。

## 3. 三项职责，一种体验

框架区分三项职责：

- **提供方：**内容与数据契约、受支持的操作、获准的界面元素、策略，以及可用的默认应用。
- **用户定义的体验：**关于呈现、交互、组织、所请求能力，以及受支持操作或工作流引用的可复用选择。
- **私人实例：**个人账户或数据源绑定、访问决策、记录、笔记、执行状态和历史。

可移植的**界面包（package）**是可复用体验的一种技术表示，不是 UDI 思想的全部，也无需在产品中作为文件呈现。概念上，设 \(P=(M,C,S,V,A)\)，分别表示元数据、能力请求、数据源契约、视图与组织方式，以及受支持的操作；设 \(I=(B,G,D,H)\)，表示私人绑定、授权、数据和历史。提供方运行时在能力与策略约束下计算体验 \(R(P,I)\)。分享传递的是 \(P\)，不是 \(I\)。

这一模型不要求任意工作流编程，也不声称当前模式能够表达所有领域。Core 0.1 只实现了较小的研究配置；更广泛的提供方契约和工作流语义，需要各自注明版本的配置及校验。

这是一项结构边界，不是非干扰性证明。标题、视图标签或介绍仍可能含有私人文本。分享时必须解释哪些内容会被带走，并允许审阅。生产部署还可能需要信息分类、来源记录与扫描。兼容性取决于接收方支持的配置、能力与策略；一份定义通过校验，并不能证明无关的应用也能运行它。

## 4. 创作与复用

面向普通用户的生命周期是：**试用 → 使用 → 选择工作区并授权 → 个性化 → 分享链接**。用户在替换界面前看到有意义的预览。接收方实例连接自己的数据，并单独授予访问权限。用户可以继续修改采用的体验，再分享自己的版本。

智能体请求会成为针对特定修订版本的提案。宿主校验有界操作集，将其应用到副本，校验结果并展示有意义的变化。批准后才替换当前定义。直接控件也可以采用同一修订路径；权限变化和实际操作还需要各自适当的审阅。

基础修订版本或精确的基础定义不再匹配时，提案必须失败。撤销会创建一个包含先前定义的新修订，不会逆转已完成的外部操作，也不会恢复旧的授权。框架实现还应保留让用户能够理解的、回到提供方默认体验的路径。

智能体负责创作提案，不能自行授权。模型声称“这是只读操作”，不能覆盖提供方操作目录的定义。共享界面的能力请求不是接收方的批准。查看、复制或采用体验，不得静默带入他人的权限。

## 5. 运行时职责

渲染应使用获准的组件词汇表，而不是执行任意生成的前端代码。逻辑数据源通过实例自己的绑定解析。操作调用固定、效果已知的处理程序。数据组织和工作流必须遵守提供方实际支持的语义，不能仅从外观推断其效果。

对于能力 \(c\)、实例 \(i\) 和资源 \(r\)，生产环境的策略决策至少应满足：

\[
\operatorname{allow}(c,i,r)=
\operatorname{declared}(c,P)\land
\operatorname{granted}(c,i)\land
\operatorname{inScope}(r,i)\land
\operatorname{hostPolicy}(c,r).
\]

浏览器原型演示声明、授权和本地数据绑定检查，没有提供可信的外部资源网关。生产网关必须将凭证保存在共享定义和不受信任的客户端代码之外，在每次调用时执行资源范围限制，并支持独立于模型行为的撤权。

敏感效果需要精确预览和单独的执行授权。本原型的本地笔记处理程序在执行时重新计算内容，并再次检查访问权限。浏览器确认用于演示交互，不是持久化的一次性授权令牌。外部写入、并发工作流及恢复机制，需要更强的事务与批准语义。

## 6. 当前参考实现

v0.4.0 应用提供桌面版 UDI Studio 和[手机版 UDI Pocket](MOBILE.md)，均支持简体中文与英文。两者使用同一份 **Core 0.1 研究配置**，因此只能说明一个实现内的共享行为，不能证明独立运行时之间的互操作。

主要路径包含示例数据可视预览、明确的**使用这个界面**操作、工作区选择与访问授权、智能体或设置式个性化，以及链接分享。用户可以通过表单创建个人研究工作区，无需必须处理 JSON。[社区指南](COMMUNITY.md)说明复用流程。项目示例与真实公开帖子分别标识。文件导入/导出与 GitHub 发布保留为高级工具，而非普通用户的入口。

可执行配置支持实验指标、结果表、模型表现图、截止日期与研究文献库。有界变化包括失败结果筛选、按模型分组、视图显隐、专注布局，以及经确认的本地审阅笔记。从 Aurora 切换到 Atlas 或个人本地工作区，会重新绑定逻辑数据源，不会迁移他人的记录或授权。预览使用虚构的公开示例数据；采用定义时清除现有访问权限，留待重新审阅。

托管版智能体对话使用有限的确定性命令语法，**没有托管大语言模型**。可选的本地 Ollama 桥接服务可以提出同一组受支持操作。设备用户能够检查与修改本地数据和浏览器检查逻辑。音乐、阅读、旅行、照片及效率服务尚未接入，也没有通用工作流引擎。

## 7. 与先行工作的关系

UDI 延续了终端用户编程、自适应界面和人类能力增强等领域的长期研究。例如，SUPPLE 将界面生成表述为基于功能需求、用户及设备特征求解的优化问题。本提案侧重于对持久体验的持续用户创作与复用，包括它与数据及受支持效果之间的受控连接。参见 [SUPPLE，Gajos 和 Weld，2004](https://www.eecs.harvard.edu/~kgajos/papers/2004/gajos04supple.shtml)。

现代系统提供互补的组成部分。A2UI 通过声明式组件描述智能体生成的界面；AG-UI 为智能体与前端交互提供结构；MCP Apps 提供嵌入宿主的工具界面；json-render 提供组件目录约束下的生成与渲染。[相关工作分析](RELATED-WORK.md)说明其作用，以及尚未实现兼容适配器的边界。

本项目提出的是**可检验的生命周期架构与产品模型**，不声称取代这些项目。更强的新颖性主张需要更广泛的文献综述，以及对实现和用户结果的直接比较。

## 8. 可证伪的假设

1. **修订成本：**任务变化时，普通用户调整体验所需投入少于重新创建或编辑源代码。
2. **复用成本：**另一人试用体验并连接自己数据的效率，高于从头构建等效配置。
3. **控制权理解：**区分所请求的功能、已授权访问和操作批准，有助于理解智能体的权限。
4. **连续性：**经过审阅的增量变化和撤销，比未经审阅的整体重新生成更能保持任务连续性。
5. **分享易用性：**相比技术性界面包交换，可视预览与熟悉的链接分享减少错误和求助。

这些都是假设，仓库的符合性检查不能证明它们成立。研究应纳入系统开发者之外的普通用户，比较任务完成、纠正成本、无障碍、控制感、可预测性、复用失败和隐私事件。模型延迟与成本是额外指标，不能替代用户结果。

## 9. 局限与后续工作

通用框架是提案草稿，不是已批准的标准。当前配置面向研究领域，可移植性只限于兼容的本参考运行时安装。分享链接不能证明跨平台或跨运行时兼容；公开社区动态也不能证明用户采用或有效治理。

后续工作包括评估未见过的语言请求、与普通用户研究完整复用闭环、在可信网关后实现一个真实提供方适配器，以及构建注明版本的渲染器适配器。提供方集成应演示有用的内容与一种超出外观修改的受支持操作。更广泛的工作流、迁移、后台执行和具备治理机制的分发，需要独立的契约、实现和证据，详见[路线图](ROADMAP.md)。

## 10. 结论

UDI 提出：具备能力的平台既可以提供可用的默认应用，也可以让人们塑造并分享自己持久使用它的方式。可复用定义、私人实例、经过审阅的修订和由运行时管控的能力，使这一提案具体到足以实现与检验。研究原型给出了范围受限的生命周期实例；更广泛的有效性仍需研究与工程实践回答。
